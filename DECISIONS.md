# DECISIONS.md

## Вариант

Номер варианта: 26

Часть А: R3 — submit блокируется, если у сотрудника уже есть активная командировка
(статус SUBMITTED или APPROVED). Проверка в BusinessTripService.create.

Реализовано: у заявки появилось поле employee (сотрудник). BusinessTripService.create
не создаёт новую заявку, пока у этого сотрудника есть заявка в SUBMITTED или APPROVED,
и выбрасывает IllegalStateException с id и статусом мешающей заявки. Та же проверка
повторяется в BusinessTripService.submit: иначе можно было бы создать две заявки
в DRAFT и отправить обе. После перехода заявки в REJECTED, CANCELLED или COMPLETED
сотрудник снова может оформить командировку. Заявки других сотрудников не мешают.

Часть Б: addActiveTripsCount(BusinessTripService service) → int — количество активных
командировок (SUBMITTED или APPROVED). Использует service.findByStatus().

Реализовано: статический метод BusinessTripService.addActiveTripsCount складывает размеры
списков findByStatus(SUBMITTED) и findByStatus(APPROVED). Для null выбрасывается
NullPointerException с сообщением «service is null».

Проверки варианта в SelfCheck: 19–23 (часть А), 24–26 (часть Б); строки V-01…V-04
и COUNT в data/sample.csv.

## Решение 1. Проверка варианта в сервисе, а не в BusinessTrip

Формулировка: правило «одна активная командировка на сотрудника» проверяется
в BusinessTripService (create и submit), правила переходов R3–R9 остаются в BusinessTrip.

Альтернатива: хранить в BusinessTrip ссылку на список всех заявок сотрудника
и проверять правило внутри submit().

Обоснование: одна заявка знает только своё состояние, а правило варианта касается
нескольких заявок. Список заявок есть только у сервиса, поэтому проверка там. Так
BusinessTrip остаётся моделью без лишних зависимостей и тестируется отдельно,
а сервис координирует заявки (разделение модели и сервиса, раздел 4.10).

## Решение 2. Общая проверка статуса и одно место для порога R6

Формулировка: переходы «только из одного статуса» (R3, R5, R8) проверяет приватный
метод requireStatus(expected, target), сообщение об ошибке строит transitionError.
Порог длины причины вынесен в константу MIN_REASON_LENGTH = 10.

Альтернатива: писать if и текст исключения заново в каждом доменном методе,
а число 10 указывать прямо в reject().

Обоснование: сообщение «Ошибка перехода: X → Y недопустим» везде одинаковое,
доменные методы короче 10 строк. Изменение порога 10 → 20 затрагивает одну строку
в одном классе, и тексты ошибок обновляются автоматически.

## Ответы на контрольные вопросы

### Вопрос 1. Какая проверка защищает программу от наиболее вероятной ошибки входных данных и где она расположена?

Самая вероятная ошибка — перепутанные или незаполненные даты командировки: при ручном
вводе или чтении CSV легко поменять start и end местами или оставить поле пустым.
Защищает от этого правило R2 в конструкторе BusinessTrip: start и end не null
и !start.isAfter(end), иначе IllegalArgumentException("start must be <= end").
Проверка стоит в конструкторе, поэтому объект с неверными датами вообще не создаётся
(fail-fast) и все остальные методы, включая complete с проверкой R9, работают уже
с корректными датами. Граница включена: start = end допустимо, это командировка
на один день (проверка 30 в SelfCheck). Рядом проверяется R1 (id не пустой).
В data-driven режиме такие строки (T-04 и строка без id) дают SKIP, и программа
продолжает работу со следующей строкой.

### Вопрос 2. Какой метод или класс содержит ключевое бизнес-правило и почему он размещён именно там?

Ключевые правила — переходы состояний R3, R5, R7, R8 в доменных методах BusinessTrip:
submit, approve, reject, cancel, complete. Они размещены в BusinessTrip, потому что
заявка сама хранит свой status, и только она знает, из какого статуса возможен переход.
Поле status private и не имеет setter, поэтому изменить его в обход этих проверок
нельзя (R10). Общая часть вынесена в приватный requireStatus. Правило моего варианта
размещено иначе — в BusinessTripService.create и submit, потому что оно сравнивает
несколько заявок одного сотрудника, а список заявок хранит только сервис. Так каждая
проверка находится там, где есть все нужные для неё данные, и сервис не дублирует
правила переходов: для отправки он вызывает trip.submit(), где R3 проверяется заново.

### Вопрос 3. Как Activity-диаграмма отражает один конкретный участок вашего кода?

Возьмём ребро APPROVED → COMPLETED с подписью «complete(today), R8: только из APPROVED,
R9: today >= end». В коде это метод complete(LocalDate today): первая строка
requireStatus(APPROVED, COMPLETED) соответствует условию R8 и выбрасывает
IllegalStateException, если статус другой. Затем проверка today.isBefore(end)
соответствует условию R9: если сегодня раньше даты окончания, переход запрещён.
Только после обеих проверок выполняется status = COMPLETED, то есть стрелка
в узел COMPLETED. На второй диаграмме этот же путь показан блоками A1 (допустимость
перехода) и A2 (данные операции). Узел COMPLETED не имеет исходящих рёбер — это
соответствует isTerminal() в cancel(). Этот путь проверяют SelfCheck 15 и 17,
а также строки T-10 и T-12 в sample.csv.

### Вопрос 4. Какое изменение требования должно затронуть минимальное количество классов и почему?

Изменение минимальной длины причины отклонения с 10 на 20 символов. Оно затрагивает
один класс BusinessTrip и одну строку: константу MIN_REASON_LENGTH. Метод reject
сравнивает длину именно с этой константой, а текст исключения собирается из неё же,
поэтому логику менять не нужно. BusinessTripService, TripStatus и data-driven режим
не меняются. В SelfCheck меняются только ожидания проверок 10, 11 и 27, которые
специально проверяют границу. Для сравнения: если активными станут считаться и заявки
в DRAFT, придётся менять уже два места — метод isActive() в BusinessTrip, на который
опирается проверка сервиса, и addActiveTripsCount, который считает по статусам.
Поэтому изменение порога R6 и есть самое локальное.

## Фрагмент кода для анализа

```java
public void setStatus(TripStatus status) {
    this.status = status;
}
```

Открытый setter нарушает инкапсуляцию: внешний код меняет статус напрямую, минуя
доменные методы и их проверки. Например, trip.setStatus(TripStatus.COMPLETED) переводит
черновик сразу в COMPLETED, хотя R8 разрешает это только из APPROVED, а R9 — только
после даты окончания; так же можно «оживить» отклонённую заявку. Исправление — удалить
setter и менять status только в submit, approve, reject, cancel и complete, где каждый
переход проверяется. Поэтому по R10 поля status и rejectionReason объявлены private
и не имеют setter: единственный путь изменить их проходит через проверки R3–R9.
